# User Stories (Quinoto Software Factory MVP)

**Proposal ID:** 2026-11-08-quinoto-software-factory-mvp
**Prefijo:** SWFC-f4c2
**Estado:** proposed

| ID | User Story | Criterios de Aceptación | Prioridad | Estimación | Servicio |
|---|---|---|---|---|---|
| US-SWFC-f4c2-001 | Como **desarrollador**, quiero un monorepo con tooling base (pnpm, TypeScript estricto, lint y formato), para construir todos los servicios con contratos compartidos y sin configuración duplicada. | - [ ] `pnpm install` y `pnpm build` funcionan desde la raíz<br>- [ ] TypeScript estricto habilitado en todos los paquetes<br>- [ ] Lint y formato corren sobre todo el workspace | P1 | M | platform |
| US-SWFC-f4c2-002 | Como **desarrollador**, quiero un pipeline de CI que ejecute lint, typecheck y tests en cada PR, para detectar regresiones antes de mergear. | - [ ] Un PR dispara lint, typecheck y unit tests<br>- [ ] El PR queda bloqueado si el pipeline falla<br>- [ ] El pipeline corre en menos de 10 minutos | P1 | S | platform |
| US-SWFC-f4c2-003 | Como **operador**, quiero levantar la instancia completa con Docker Compose, para self-hostear la factory sin instalar dependencias en el host. | - [ ] `docker compose up -d` levanta web, api, worker, Postgres y Redis<br>- [ ] `/readyz` responde 200 con dependencias sanas<br>- [ ] La instalación en host limpio tarda ≤ 30 minutos | P1 | M | platform |
| US-SWFC-f4c2-004 | Como **desarrollador**, quiero esqueletos de API y UI con healthchecks y validación de entorno, para tener una base ejecutable sobre la que iterar. | - [ ] La API expone `/healthz` y `/readyz`<br>- [ ] La UI muestra una pantalla inicial y maneja error de API caída<br>- [ ] Una variable de entorno inválida detiene el arranque con mensaje claro | P1 | M | platform |
| US-SWFC-f4c2-005 | Como **operador**, quiero instalar la GitHub App mediante manifest flow, para habilitar la integración con permisos mínimos sin crear credenciales a mano. | - [ ] El manifest flow crea la app y guarda app ID, private key y webhook secret cifrados<br>- [ ] Los permisos solicitados son contents, pull_requests y metadata<br>- [ ] Un webhook con firma inválida se rechaza con 401 | P1 | L | github-adapter |
| US-SWFC-f4c2-006 | Como **desarrollador**, quiero conectar un repositorio y crear un proyecto eligiendo branch base, para empezar a trabajar sin clonar ni configurar nada localmente. | - [ ] El selector lista repos con su branch por defecto<br>- [ ] Al confirmar se crea un proyecto en estado `ready`<br>- [ ] Si faltan permisos, la UI explica el problema y no crea el proyecto | P1 | M | web-ui |
| US-SWFC-f4c2-007 | Como **operador**, quiero que los tokens de GitHub, Railway y LLM se cifren en reposo y nunca se expongan, para cumplir el acuerdo PA-005. | - [ ] Solo se persiste ciphertext y nonce<br>- [ ] La API pública nunca devuelve el token<br>- [ ] Un test escanea DB y logs y no encuentra secretos en claro | P1 | M | security |
| US-SWFC-f4c2-008 | Como **desarrollador**, quiero ejecutar el workflow QuinotoSpec con etapas y gates explícitos, para que el proceso no se saltee pasos ni dependa de la memoria de cada persona. | - [ ] Las etapas avanzan en orden y registran timestamps<br>- [ ] Una transición inválida se rechaza sin cambiar el estado<br>- [ ] Los gates bloquean el avance sin artefactos o aprobaciones | P1 | XL | orchestrator |
| US-SWFC-f4c2-009 | Como **tech lead**, quiero aprobar artefactos desde la UI con registro de decisor y alcance, para que el gate humano quede auditado. | - [ ] La bandeja lista aprobaciones pendientes<br>- [ ] Aprobar registra actor, timestamp y alcance<br>- [ ] Sin aprobación, la etapa siguiente queda bloqueada | P1 | M | web-ui |
| US-SWFC-f4c2-010 | Como **desarrollador**, quiero reintentar una etapa fallida desde su checkpoint, para no repetir trabajo ya validado. | - [ ] El reintento reanuda en la etapa fallida<br>- [ ] Los artefactos de etapas previas quedan intactos<br>- [ ] El timeline muestra cada intento por separado | P1 | M | orchestrator |
| US-SWFC-f4c2-011 | Como **operador**, quiero que cada sesión de agente corra en un contenedor efímero en Railway, para aislar la ejecución y controlar el costo. | - [ ] Se crea un servicio por sesión y se destruye al terminar<br>- [ ] Si el healthcheck falla, el servicio se destruye y la sesión falla<br>- [ ] Un servicio huérfano se termina en la próxima reconciliación | P1 | XL | railway-adapter |
| US-SWFC-f4c2-012 | Como **desarrollador**, quiero ver los logs del agente en vivo y poder cancelar la sesión, para detectar desvíos temprano. | - [ ] Los eventos llegan a la UI con latencia ≤ 3 s<br>- [ ] Cancelar detiene el agente y destruye el contenedor<br>- [ ] El log queda disponible después de terminar | P1 | L | agent-runtime |
| US-SWFC-f4c2-013 | Como **operador**, quiero que los contenedores huérfanos se detecten y destruyan automáticamente, para evitar costos ocultos. | - [ ] La reconciliación detecta servicios sin sesión activa<br>- [ ] El servicio se termina y se registra en auditoría<br>- [ ] La reconciliación corre periódicamente y es idempotente | P1 | M | agent-runtime |
| US-SWFC-f4c2-014 | Como **desarrollador**, quiero revisar el diff producido por el agente y abrir un PR con contexto, para entregar cambios revisables. | - [ ] El diff mostrado coincide con el PR creado<br>- [ ] El PR incluye resumen, artefactos y sesión vinculados<br>- [ ] Rechazar el diff no crea PR y encola un reintento con feedback | P1 | L | github-adapter |
| US-SWFC-f4c2-015 | Como **tech lead**, quiero garantizar que la app nunca escriba directo en `main`, para proteger la rama principal. | - [ ] Toda escritura va a un branch de trabajo<br>- [ ] Con branch protegido, la app falla de forma segura y explica el motivo<br>- [ ] Un intento de escritura a `main` se rechaza y se audita | P1 | M | github-adapter |
| US-SWFC-f4c2-016 | Como **operador**, quiero disparar un deploy en Railway desde la app y ver su estado, para cerrar el ciclo sin cambiar de herramienta. | - [ ] Se puede vincular proyecto, servicio y entorno de Railway<br>- [ ] El deploy muestra building, success o failed con URL<br>- [ ] Un deploy fallido enlaza a los logs de Railway | P1 | L | railway-adapter |
| US-SWFC-f4c2-017 | Como **product owner**, quiero un dashboard multi-proyecto con etapa, sesiones, PRs y deploy, para saber dónde está trabado el trabajo sin preguntar. | - [ ] El dashboard muestra todos los proyectos y su etapa actual<br>- [ ] Los proyectos con acción requerida se destacan<br>- [ ] Los estados vacío, loading y error están cubiertos | P1 | M | web-ui |
| US-SWFC-f4c2-018 | Como **responsable de seguridad**, quiero auditoría append-only y redacción de secretos en todos los sinks, para investigar incidentes sin filtrar credenciales. | - [ ] Cada acción sensible genera una entrada inmutable<br>- [ ] Los secretos se redactan antes de persistir y de transmitir<br>- [ ] Un intento de modificar la auditoría se rechaza | P1 | M | security |
| US-SWFC-f4c2-019 | Como **operador**, quiero documentación de instalación, upgrade, backup y restore, para operar la instancia sin depender del equipo core. | - [ ] La guía de instalación funciona en host limpio<br>- [ ] El upgrade preserva datos y permite rollback por tag<br>- [ ] Un backup se restaura en una instancia limpia | P1 | L | platform |
